# План реализации и делегирование

## Визуальная адаптация — 17 октября 2026

По запросу пользователя оформление Next.js адаптировано по примеру [Janapost](https://www.janapost.kz/ru/home): зелёный `#008C00`, светлый фон, белые скруглённые карточки, верхняя навигация и мобильное меню. На входе, в шапке и иконке используется предоставленное изображение Jańa Digital; файл включён в standalone Docker-сборку. Главная показывает действующие показатели и ведёт в существующие разделы Digital HR. Функциональные контракты и демонстрационный процесс согласования не менялись. Проверки и их ограничения описаны в verification.md.

По уточнению пользователя вспомогательные подписи и общий footer удалены. В шапке и на входе используется новое прозрачное изображение Jańa Digital с переходом на главную; квадратная иконка сохранена. Слева добавлен переключатель-заглушка «Русский / Қазақша» без реализации перевода. Правый колокольчик сохраняет переход к уведомлениям, мобильное меню — доступ ко всем разделам роли.

## Порядок

Текущая итерация по запросу пользователя: очередь личных решений и точные счётчики; связанные уведомления и прочтение всех; человекочитаемый аудит с фильтрами, страницами и CSV; календарь команды; отзыв/замена ожидающей заявки и подтверждаемая HR отмена будущего отпуска; поиск и структура каталога сотрудников; отдельная панель интеграций. Академия и помощник функционально не расширяются. Принятые для отмены ограничения — только правила демонстрации, не решение Q01–Q07.

1. Зафиксировать контракты, роли и ограничения MVP; подготовить окружение.
2. Реализовать миграцию, seed, вход и read-only профиль.
3. Реализовать заявку, последовательные этапы «руководитель → HR», атомарную историю/аудит/уведомления и идемпотентность.
4. Параллельно собрать интерфейс по контракту API.
5. Добавить назначенный курс, тест и помощника с источниками/отказом.
6. Подключить интерфейс к реальному backend, собрать контейнеры и проверить сквозной путь.
7. Проверить права, сохранность заполненной базы после миграции и повторных команд; записать пределы проверки.

## Делегирование

Технический лидер владеет docs/api-contract.md, общими моделями, миграциями и интеграцией. Изменения контракта требуют согласования до параллельной работы.

| Задача | Область записи | Критерий готовности |
| --- | --- | --- |
| Frontend | frontend/ | Все страницы работают по контракту; адаптивная компоновка, состояния загрузки/ошибки, без вымышленных API |
| Backend | backend/ | Авторизация, объектные права, атомарные изменения, аудит, тесты |
| Проверка | backend/tests/, отчёт | Изоляция сотрудников/команд, собственное согласование запрещено, повтор команды, сохранение данных |
| Инфраструктура | compose.yaml, README.md | Понятный запуск, переменные окружения, сохранение данных, healthchecks |

Проект по прямому указанию пользователя выделен в самостоятельный Git-репозиторий: единственный origin — https://github.com/bshakaryan/digital-hr.git, ветка main. Отправлять изменения только туда; родительский репозиторий для Digital HR не используется. Ветки и PR нужны при совместной работе. Не коммитить чужие файлы. Интегрировать небольшими порциями, сначала контракты и backend, затем вызовы UI.

Следующий этап после демо: согласованные RU/KZ-материалы и разрешённый LLM-провайдер, SSO, реальные интеграции, PostgreSQL-конкурентные тесты в CI. Каждый пункт отдельной задачей, с собственными критериями приёмки.

## Расширенное рабочее пространство

Уточнение уведомлений: раздел по умолчанию показывает непрочитанные; прочтение убирает событие из активного списка и с главной. Прочитанные доступны в отдельной вкладке с постоянной серверной очисткой списка. Миграция 0007 добавляет `cleared_at`, исторические миграции не меняются; аудит и содержимое событий сохраняются. Физический срок хранения остаётся в Q07.

Реализованы серверная очередь доступных решений, отображение ожидания на этапе, исправленные счётчики и подписи дней; связанные уведомления с автором, переходами и прочтением всех; аудит с ФИО, фильтрами, пагинацией и CSV; командный календарь с пересечениями; каталог с поиском, фильтрами и структурой; отдельный HR-раздел интеграций и очередь передачи/возврата. Отзыв/атомарная замена ожидающей заявки и запрос/решение отмены будущего отпуска дополнены командным журналом и outbox возврата. Это демо-процесс из decisions.md, а не утверждение кадровых правил. Миграция 0006 дополняет схему, прежние миграции не менялись. Реальные проверки и ограничения — verification.md.

## Выполнено в первой итерации

Контракты, миграции и seed, backend, адаптивный интерфейс, последовательный сценарий заявки, Academy, уведомления, аудит и помощник по источникам реализованы. Актуальное число тестов и браузерных проверок указано в verification.md. Docker Compose дополнен запуском без локальных Python/Node.js, healthcheck интерфейса, выбором портов и CI-сценарием с PostgreSQL. Генеративный RAG не реализован. Фактические проверки Docker/PostgreSQL и их пределы — в verification.md.

Следующей итерацией подключён отдельный HTTP mock 1С:ЗУП с собственным хранилищем, календарным расчётом без праздничных дат Казахстана (2026–2028), текущим остатком и идемпотентной регистрацией отпусков. Снимок расчёта сохраняется в заявке; пересечения запрещены. Финальное одобрение атомарно сохраняет локальное списание и outbox; worker передаёт команду с повтором и сохраняет квитанцию. Ожидающие заявки не резервируют остаток. Начисления, рабочие годы, переносы и отмены требуют согласованных кадровых правил. Контракт и путь к реальной базе описаны в zup-integration.md; работа с конфигурацией компании не подтверждена.

Подготовлен real-режим того же адаптера: Basic/Bearer, TLS/корпоративный CA/mTLS, read-only проверка соединения и шаблон HTTP-сервиса расширения 1С. В real-режиме demo seed не запускается, а интерфейс отличает реальную базу от mock. Для фактического включения всё ещё требуются тестовая публикация конкретной ЗУП, сервисная учётная запись, GUID-сопоставление и человеческая приёмка создания документа.

По уточнённому условию кейса реализуется mock Documentolog Business с отдельным HTTP-сервисом и постоянным хранилищем. Добавлены DOCX-снимок заявки, явное создание HR, отдельные статусы, имитация подписи/отказа, webhook и панель связи. Подготовлен тонкий real-адаптер публичного Business API; фактические аккаунты, проверка ЭЦП и корпоративный Platform не входят в этот демонстрационный этап. Проверки — verification.md.

Делегирование фактически использовано для frontend и backend-тестов в первой итерации. Контракты, модели, миграция, инфраструктура, интеграция и финальный браузерный прогон выполнялись основным агентом. Оценённый извлекающий RAG, ограниченная RU/KZ-поддержка, серверный XP и вопросы по назначенному курсу добавлены отдельно; результаты и пределы — в verification.md. Генеративный LLM и полноценная локализация остаются открытыми задачами. Результат каждого направления принимает человек по demo-scenarios.md.
