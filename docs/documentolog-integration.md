# Documentolog: mock API и будущая интеграция

Для текущего кейса допускаются mock API и тестовые данные. Compose поднимает отдельный `documentolog-mock` с SQLite в volume `documentolog_mock_data`. Это наш сервис по опубликованному контракту Documentolog Business, а не установленный Documentolog. ЭЦП/eGov QR и юридически значимая подпись не выполняются.

## Сквозной сценарий

1. Сотрудник получает расчёт из mock 1С:ЗУП, отправляет заявку; руководитель и HR принимают решения.
2. Финальное решение HR списывает дни и передаёт отпуск в mock 1С:ЗУП по существующему процессу. Documentolog не меняет этот момент учёта.
3. HR открывает согласованную заявку и нажимает «Создать демонстрационный документ». Backend сохраняет неизменяемый DOCX заявления, SHA-256, ключи доступа к файлу/webhook и команду отправки. Форма демонстрационная, не утверждённая кадровая форма компании.
4. Backend вызывает `POST /json/external/oauth/token` mock с `api-key`. В `aAttachments` передаётся адрес сохранённого файла; mock скачивает файл по HTTP и сохраняет SHA-256. Ответ содержит токен сессии. В браузер не передаётся сервисный API-ключ.
5. HR открывает ссылку сессии. Страница явно обозначена как mock; показывает номер, получателя, SHA-256 и позволяет скачать заявление. Человек выбирает «Имитировать подписание» либо «Имитировать отказ».
6. Mock сохраняет результат до отправки webhook. Backend получает `document_completed` либо `signer_declined`, обновляет отдельный статус, аудит и уведомление. Карточка обновляется кнопкой «Обновить статус». Период, решение HR, списание дней и квитанция ЗУП не меняются.

Повтор подготовки той же заявки возвращает сохранённую сессию; другой получатель → 409. Mock поддерживает `Idempotency-Key`: одинаковое тело возвращает старую сессию, другое тело → 409. Повтор webhook не создаёт повторного уведомления/аудита и не ухудшает завершённый статус. `signer_signed` — подпись отдельного участника, не завершение документа.

Если backend недоступен, mock сохраняет решение, сообщает о недоставленном webhook и позволяет повторить то же действие. Фоновая доставка callback не реализована. После перезапуска документы остаются в PostgreSQL и отдельном SQLite. Не удалять volume при демонстрации сохранности.

## Права и ограничения

Создание и получение ссылки инициатора доступны HR; собственная заявка HR не отправляется от его имени. Статус виден тем же пользователям, которым доступна заявка. Посторонний сотрудник получает 404. Файл и webhook имеют разные случайные capability-токены по 256 бит со сроком 30 дней; они не включаются в ответ статуса. Ссылки сессии также являются секретами доступа. В Compose access logs backend/mock отключены, чтобы URL не попадали в логи. Внешний proxy должен скрывать эти URL в логах и использовать HTTPS.

Mock скачивает файлы и вызывает webhook только у `DOCUMENTOLOG_MOCK_BACKEND_URL` с фиксированными префиксами маршрутов, без redirect. Событие другого внешнего документа → 409. Ссылки просмотра принимаются только с origin настроенного Documentolog.

Моделируются один получатель и одно заявление на заявку. Замена файлов, отмена, несколько обязательных подписантов и приказы требуют согласования. Правило «сначала подписи, затем проведение в ЗУП» не включено без согласования процесса; сейчас подписание идёт отдельно после одобрения HR.

Расширенный демо-цикл отпуска разрешает отмену только пока Documentolog-документ ещё не создан. После подготовки любого документа отмена блокируется, поскольку аннулирование/сверка внешней сессии пока не реализованы. Создание документа повторно проверяет статус под блокировкой заявки и не может пройти после начала отмены. Статус подписания обновляется в открытой карточке автоматически каждые 15 секунд и вручную; уведомление открывает исходную заявку.

## Настоящий API и его границы

Адаптер использует опубликованный API Documentolog **Business**: `POST /json/external/oauth/token`, заголовок `api-key`, поля `aAttachments`, `sSetWebhookUrl`, `mRecipient`, `sSender`, форму `/external/sign/embedded?sParams=<access_token>` и события `document_sent`, `signer_signed`, `signer_declined`, `document_completed`.

Источник: [официальная документация Business](https://osihub.documentolog.com/integrations-business/api), проверена 16.10.2026. Нужны регистрация организации и API-доступ на соответствующем тарифе. Корпоративный Platform может иметь другой контракт; совместимость не подтверждена.

В публичном описании не заявлены идемпотентность создания сессии, поиск сессии по нашему ключу и криптографическая подпись webhook. Backend сохраняет `creating` до сетевого вызова и не отправляет повторно после неопределённого результата; таймаут → `needs_review`. Это сохраняемая команда с однократной попыткой, не очередь автоматических повторов. Падение процесса после отправки тоже не приводит к повторному созданию. В real-режиме `document_completed` означает `completed_reported`: требуется проверка документа HR, сообщение не считается проверенной ЭЦП. Автоматическая проверка подписей/архивирование подписанного файла не реализованы.

## Настройки

Docker: по умолчанию `DOCUMENTOLOG_MODE=mock`, внутренний адрес `http://documentolog-mock:8400`, страница `http://localhost:8400`. Порт меняется через `DOCUMENTOLOG_PORT`; публикация только на loopback. Новая `.env` содержит отдельный `DOCUMENTOLOG_API_KEY`; для старого демо допускается fallback на JWT_SECRET, production требует отдельного ключа.

Для локального Python задать параметры из `.env.example`, экспортировать переменные mock-процесса и запустить `uvicorn app.mock_documentolog:app_factory --factory --host 127.0.0.1 --port 8400 --no-access-log` с `PYTHONPATH=backend`. `DOCUMENTOLOG_MOCK_DATABASE` — путь SQLite; `DOCUMENTOLOG_MOCK_BACKEND_URL` — origin backend. У backend также отключить access logs. `DOCUMENTOLOG_MODE=disabled` отключает новые отправки.

Будущее подключение: `DOCUMENTOLOG_MODE=real`, API-ключ организации Business, ИИН/БИН отправителя `DOCUMENTOLOG_SENDER`, ИИН получателя, HTTPS `DOCUMENTOLOG_DOCKER_BASE_URL`/`DOCUMENTOLOG_BROWSER_URL`, публичные HTTPS `DOCUMENTOLOG_PUBLIC_URL`/`DOCUMENTOLOG_CALLBACK_URL`. Старые mock-документы не отправляются в другой контур автоматически. До production согласовать шаблон, подписантов, защиту webhook, сверку неоднозначных отправок, хранение и проверку подписанных файлов. Одна смена URL не означает готовность production.
