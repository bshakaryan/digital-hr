# Архитектурные решения

## Принято для реализации MVP

- Next.js и TypeScript для адаптивного интерфейса; FastAPI, SQLAlchemy 2, Alembic и PostgreSQL для backend.
- Один backend с доменными модулями. Для демонстрации внешней границы запущен отдельный HTTP mock 1С:ЗУП и worker доставки; отдельный брокер и Redis не используются.
- Кадровые данные доступны только для чтения. Вымышленные профили впервые загружаются seed-командой по HTTP из отдельного mock 1С:ЗУП; связь сохраняется в `employees.zup_id`. Seed не перезаписывает существующие кадровые поля и пароли. Текущий остаток читается из mock по HTTP, без скрытого перехода на устаревший локальный снимок.
- Сотрудник видит себя и свои заявки. Руководитель дополнительно видит прямых подчинённых и их заявки. HR видит все демонстрационные профили и заявки. Руководитель не согласовывает собственную заявку.
- Демо-процесс последовательный: `submitted → manager_approved → approved`. На первом этапе решение принимает непосредственный руководитель, на втором — HR. Отклонение на любом этапе переводит заявку в `rejected`; самостоятельное согласование запрещено. Заявка не создаётся, если в профиле отсутствует руководитель с ролью manager, чтобы не возникал процесс без первого согласующего.
- Создание заявки атомарно сохраняет историю, аудит и уведомления. Повтор с тем же Idempotency-Key и тем же телом возвращает прежний результат; другое тело с тем же ключом даёт 409. Изменение статуса использует version для защиты от устаревшего решения.
- Активный список и блок «На связи» показывают непрочитанные уведомления. Прочитанные доступны отдельно и могут быть убраны командой «Очистить прочитанные». Сервер сохраняет `cleared_at` и аудит каждого первого удаления из списка; повтор безопасен, чужие и непрочитанные события не затрагиваются. Очистка не удаляет историю или записи физически; срок хранения остаётся открытым Q07.
- Расчёт отпуска возвращает HTTP mock 1С:ЗУП: календарные дни включительно, за исключением национальных и государственных праздничных дат Казахстана. Обычные и перенесённые выходные, 7 января и первый день Курбан-айта не исключаются. Версия демонстрационного календаря `kz-statutory-2026-v1`, поддерживаются 2026–2028 годы; за пределами диапазона сервер отказывает, а не угадывает даты. Количество дней, исключённые даты и версия сохраняются в заявке.
- Только финальное одобрение HR атомарно создаёт локальное списание и команду передачи в mock 1С:ЗУП. Ожидающие заявки дни не резервируют, отказ не меняет остаток. Проверка остатка повторяется под блокировкой сотрудника; изменение расчёта после отправки требует новой заявки. Пересечения активных заявок одного сотрудника запрещены, отклонённые не блокируют период. Пустой период из одних праздников отклоняется.
- Доступный остаток равен текущему остатку mock 1С:ЗУП минус локальные списания, ещё не отражённые источником. Источник возвращает ключи уже применённых команд вместе с балансом; потеря квитанции не вызывает повторного вычитания. Команда доставки хранится в outbox, использует постоянный UUID-ключ и неизменяемое тело; worker повторяет с задержкой, HR может повторить вручную. Квитанция видна в заявке; решение HR и подтверждение источника различаются. Исторические одобрения не экспортируются и не списываются задним числом.
- Помощник использует детерминированный поиск по разрешённым документам с весами полей и ограниченным RU/KZ словарём. Ответ составляет из предложений источника и ссылается на него. Без LLM, embeddings/pgvector и выдуманной confidence. Вопрос внутри курса ограничен назначенным материалом.
- Обмен по HTTP с отдельным mock-сервисом реализован. Это имитация согласованного нами расширения HTTP 1С, не штатный универсальный API ЗУП и не проверенная интеграция с базой компании. Для настоящей 1С нужны согласованный контракт расширения, сопоставление GUID и прав, публикация HTTP-сервиса и приёмка на тестовой базе.
- Условие кейса допускает mock API и тестовые данные для обеих интеграций. Documentolog моделируется отдельным сервисом по публичному API Business: сохранённый DOCX, HTTP-загрузка файла, форма с явной имитацией подписи/отказа, webhook, аудит и уведомление. Команда HR создаётся только после approved. Текущий момент списания отпуска не переносится на подпись без согласования кадровой политики. После неопределённого результата создания сессии автоматическая повторная отправка запрещена, так как реальный API не документирует идемпотентность. Настоящие API-доступы/ЭЦП не подключены; Platform требует отдельного контракта.
- Адаптер имеет явные режимы `mock` и `real`. Реальный режим использует тот же узкий контракт `jana-zup-v1`, поддерживает HTTPS с системным или корпоративным CA, mTLS, Basic-аутентификацию 1С либо Bearer через шлюз и не следует HTTP redirect. Небезопасный HTTP/отключённая проверка TLS возможны только при отдельном флаге тестового контура. Демо-seed в real-режиме запрещён: кадровые роли и учётные записи нельзя автоматически принимать из рабочей ЗУП. Наличие этого режима не означает фактическое подключение к базе компании.
- Курсы назначаются seed-командой. Завершение требует сохранённого прогресса ≥70 и правильного ответа; до завершения прогресс не превышает 99. Прогресс монотонен. 100 XP за завершённый назначенный курс вычисляются из уникальных назначений; повтор не добавляет XP. Уровень и достижения — демонстрационная механика.
- Пароли хешируются Argon2. JWT содержит идентификатор пользователя, роли читаются из базы. Секреты и демо-пароль задаются окружением. Токен интерфейс хранит только в памяти.

## Открытые вопросы

### Демо-процесс расширенного цикла заявки

По запросу на реализацию полного цикла: автор может отозвать `submitted`/`manager_approved` либо заменить такую заявку новой с повторным маршрутом «руководитель → HR». Старый период и история сохраняются; замена атомарна. Будущий одобренный отпуск можно предложить отменить целиком (`cancellation_requested`); HR, кроме самого автора, подтверждает либо отклоняет отмену. Подтверждение даёт `cancelled` и отдельную неизменяемую команду возврата в mock 1С. Возврат становится доступен только после отражения источником, потеря ответа сверяется повтором того же ключа. Исторические одобрения без команды ЗУП и заявки с созданным Documentolog-документом отменять нельзя до согласования их сверки/аннулирования. Отмена real ЗУП не реализуется без отдельного контракта. Частичная отмена, начавшийся отпуск и редактирование одобренного периода не допускаются в демо; новые даты оформляются новой заявкой после подтверждённой отмены. Это ограничения прототипа, Q01–Q07 остаются открытыми.

- Q01: правила замещения отсутствующего руководителя, маршрут для руководителей верхнего уровня и полномочия HR вне стандартной последовательности. Базовая последовательность «руководитель → HR» принята для MVP.
- Q02: корпоративные правила начисления и переноса остатка, рабочих лет, частей отпуска, дополнительных отпусков, отмены и возврата дней. Расчёт дней по календарю Казахстана реализован для демо; начисление дней и расчёт денежных отпускных не реализованы. Особые кадровые правила компании не считаются согласованными.
- Q03: реальные протоколы, источники истины и контракты 1С:ЗУП и Documentolog.
- Q04: корпоративный SSO и структура организаций/ролей.
- Q05: утверждение RU/KZ-контента, кадровых статей, сроков актуальности.
- Q06: разрешённый LLM-провайдер, размещение и передача данных.
- Q07: хранение аудита, персональных данных и эксплуатационные требования.

Открытые вопросы не блокируют демонстрацию, но соответствующие предположения не следует выдавать за правила компании.
